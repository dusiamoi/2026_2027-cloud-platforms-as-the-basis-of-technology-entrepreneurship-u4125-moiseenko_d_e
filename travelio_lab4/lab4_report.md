# Экзаменационное задание. Облачная инфраструктура Travelio Booking

**Курс:** Cloud platforms as the basis of technology entrepreneurship  
**Кейс:** Travelio Booking — агрегатор авиабилетов и отелей  
**Облачная платформа:** Google Cloud Platform (GCP)  
**Дата:** 09.11.2026

## Цель

Спроектировать облачную инфраструктуру Travelio Booking по примеру лабораторной работы №4: определить архитектуру для трёх этапов роста, описать масштабирование, быстрый поиск, отказоустойчивость, экономические факторы и риски. Целевой показатель поиска — менее 1 секунды.

## 1. Кейс и проблемы

Travelio агрегирует предложения авиакомпаний и отелей. При сезонных всплесках сервис становится нестабильным, а поиск отвечает медленно. Архитектура должна выдерживать повышенный спрос в праздники, быстро возвращать предложения и сохранять работоспособность при отказе отдельных экземпляров или зоны.

## 2. Допущения и сценарии нагрузки

Фактические метрики компании не предоставлены. Для сравнения этапов приняты модельные сценарии; перед внедрением их следует заменить данными мониторинга и прогноза спроса.

| Параметр | Пилот | Партнёры | Прод |
|---|---:|---:|---:|
| Активные пользователей в месяц (MAU) | 1 000 | 20 000 | 200 000 |
| Поисковых сессий на пользователя в месяц | 20 | 20 | 20 |
| Поисковых запросов в месяц | 20 000 | 400 000 | 4 000 000 |
| Средний трафик поиска | 0,01 запроса/с | 0,15 запроса/с | 1,5 запроса/с |
| Расчётный сезонный пик (×10) | 0,1 запроса/с | 1,5 запроса/с | 15 запросов/с |
| Поставщиков данных | тестовые | ограниченный набор | полный набор |
| Режим доступности | пилотный | несколько зон | несколько зон, HA-БД |

Множитель пика ×10 — допущение для проектирования, а не измеренная сезонность. Для продажи билетов желательно отдельно моделировать короткие пики по конкретному направлению и дате.

## 3. Архитектура и поток данных

Основной регион — `europe-west1` как предварительный вариант для европейской аудитории. Фактический регион нужно выбирать по географии пользователей, размещению поставщиков, требованиям к персональным данным и актуальным тарифам.

### Поиск

1. Пользователь отправляет запрос через HTTPS Load Balancer и Cloud Armor.
2. API Gateway проверяет токен и передаёт запрос в сервис поиска на Cloud Run.
3. Сервис поиска параллельно запрашивает индекс отелей и индекс рейсов в Elastic Cloud на Google Cloud.
4. Популярные запросы (направление, даты, базовые фильтры) обслуживаются из Memorystore for Redis с коротким TTL.
5. Результаты собираются, сортируются и возвращаются пользователю. Ответы содержат время актуальности цены и наличие.

### Обновление предложений и бронирование

1. Интеграционные адаптеры получают расписания и цены от авиакомпаний и гостиничных поставщиков.
2. События изменений публикуются в Pub/Sub. Потоковая обработка нормализует данные и обновляет поисковые индексы.
3. Сервис бронирования перед подтверждением повторно проверяет цену и доступность у поставщика: поисковый индекс не считается источником истины.
4. Подтверждённые заказы, платежные статусы и идемпотентные ключи хранятся в Cloud SQL for PostgreSQL.
5. Длительные операции и повторы выполняются асинхронно через Pub/Sub; некорректные сообщения направляются в dead-letter topic.

### Схема

```text
Пользователь
    |
HTTPS Load Balancer + Cloud Armor
    |
API Gateway
    +---------------------+---------------------+
    |                     |                     |
Search API            Booking API          User API
 Cloud Run              Cloud Run            Cloud Run
    |                     |                     |
    +--> Redis            +--> Cloud SQL HA     +--> Identity Platform
    |
    +--> Elastic Cloud: индексы рейсов и отелей
              ^
              |
Поставщики -> адаптеры Cloud Run -> Pub/Sub -> нормализация/индексация
                                      |
                                      +--> DLQ, повторная обработка

Cloud Logging / Monitoring / Trace / Alerting
Cloud Build -> Artifact Registry -> Cloud Run
```

## 4. Три состояния инфраструктуры

### 4.1. Начальное состояние (пилот)

- Cloud Run для API, поиска и адаптеров, с ограниченным `max instances`.
- Один небольшой экземпляр Elastic Cloud либо тестовая конфигурация индекса.
- Redis только для наиболее популярных запросов, если нагрузочные измерения подтвердят пользу кэша.
- Cloud SQL PostgreSQL в зональной конфигурации с резервными копиями.
- Pub/Sub для отделения обновления каталога от пользовательского запроса.
- Базовые Cloud Logging и Monitoring, бюджетные уведомления.

Компромисс: пилотная конфигурация не обеспечивает полноценное восстановление базы при отказе зоны. Её цель — проверить интеграции, качество индекса и фактический профиль запросов.

### 4.2. Тестирование партнёрами

- Раздельные проекты или окружения staging и production.
- Cloud Run сервисы масштабируются независимо; предел экземпляров задаётся по результатам нагрузочного теста.
- Elastic Cloud с несколькими узлами и репликами шардов.
- Cloud SQL увеличивается по CPU, памяти и диску; включаются PITR и проверка восстановления.
- Pub/Sub с повторной доставкой, dead-letter topic и мониторингом возраста сообщений.
- Квоты для партнёров, лимиты запросов, отдельные ключи и учёт потребления.

### 4.3. Продовое решение

- Балансировщик HTTPS, Cloud Armor, Cloud Run в нескольких зонах.
- Минимальное число тёплых экземпляров Search API для уменьшения холодного старта.
- Elastic Cloud: минимум три узла в разных зонах, реплики индексов, автоматическое масштабирование по объёму данных и CPU.
- Memorystore for Redis с высокой доступностью для горячих результатов.
- Cloud SQL PostgreSQL HA, PITR, регулярные бэкапы; доступ через пул соединений.
- Pub/Sub с dead-letter topic для интеграционных событий.
- Cloud Monitoring, алерты, трассировка, централизованные логи и контроль бюджета.
- План переключения трафика и проверенные процедуры восстановления.

## 5. Проверка пиков и целевого времени

Целевой показатель следует определить как **p95 времени ответа поиска < 1 секунды** при сезонной нагрузке. Среднее время недостаточно: оно может скрыть медленные запросы части пользователей.

Предварительный бюджет вычислительной ёмкости Search API: `пиковые запросы/с × измеренное время обработки (с) ÷ допустимая загрузка одного экземпляра`. При целевой загрузке 60% и времени обработки 0,2 с получается примерно один экземпляр на 3 запроса/с; конечное число зависит от конфигурации Cloud Run и профиля запроса.

| Проверка | Цель / действие |
|---|---|
| p95 поиска | менее 1 с при ×10 нагрузке |
| p99 поиска | измерять отдельно; установить порог после базового замера |
| Доступность | проверка при потере одного экземпляра и одной зоны |
| Индекс | тестировать фильтры по датам, направлению, цене и доступности на объёме production-каталога |
| Поставщики | ограничить тайм-аут; деградация одного поставщика не должна блокировать агрегированный ответ |
| Устаревание данных | показывать время обновления; бронирование всегда перепроверяет стоимость и наличие |
| Нагрузка | ступенчатый тест до 10× от прогноза пика и короткий burst-тест выше пика |

Чтобы удержать поиск ниже секунды, синхронный пользовательский путь не должен ждать медленные вызовы всех внешних поставщиков. Каталог индексируется заранее; актуальность подтверждается при выборе и бронировании. Это архитектурный компромисс: быстрый поиск может показывать предложение, которое изменилось у поставщика, поэтому цена и наличие перепроверяются до оплаты.

## 6. Обоснование выбора ресурсов

| Задача | Выбор | Почему |
|---|---|---|
| API и сервисы | Cloud Run | Независимое горизонтальное масштабирование и низкая операционная нагрузка; GKE оправдан, если появятся постоянные сложные процессы или требования к управлению кластерами |
| Поисковый индекс | Elastic Cloud | Подходит для полнотекстового поиска, фасетных фильтров, сортировки и репликации; независим от транзакционной БД |
| Кэш | Memorystore for Redis | Снижает повторную нагрузку на индекс для популярных запросов; кэшируем только данные с контролируемым TTL |
| Заказы | Cloud SQL PostgreSQL | Транзакции и ограничения целостности важны для бронирования, платежей и идемпотентности |
| События | Pub/Sub | Развязывает адаптеры поставщиков, индексацию и обработку повторов |
| Защита периметра | HTTPS Load Balancer + Cloud Armor | TLS, фильтрация нежелательных запросов и ограничения частоты |
| Развёртывание | Cloud Build + Artifact Registry | Повторяемая сборка и доставка контейнеров |

## 7. Экономическая модель

Без реального трафика, числа поставщиков, размера каталога, региона и тарифных условий нельзя корректно утверждать итоговую стоимость. Поэтому бюджет считается как сумма следующих компонентов и затем проверяется в Google Cloud Pricing Calculator и калькуляторе Elastic Cloud:

`месячная стоимость = Cloud Run + балансировщик/Cloud Armor + Elastic Cloud + Redis + Cloud SQL + Pub/Sub + исходящий трафик + логи/мониторинг + резерв`.

| Статья | Основной драйвер затрат | Как контролировать |
|---|---|---|
| Cloud Run | CPU/память, время запросов, минимум экземпляров | autoscaling, лимит экземпляров, профилирование |
| Elastic Cloud | количество/размер узлов, диски, реплики, трафик | измерять размер индекса и нагрузку; удалять устаревшие данные |
| Redis | размер и режим доступности | кэшировать только горячие запросы, задавать TTL |
| Cloud SQL | размер инстанса, HA, диск, бэкапы | индексы SQL, пул соединений, архивирование старых заказов |
| Pub/Sub | объём событий и повторов | идемпотентная обработка, контроль DLQ и циклических повторов |
| Трафик | размер поискового ответа, изображения отелей, egress | сжатие, CDN для изображений, пагинация |
| Наблюдаемость | объём и срок хранения логов/метрик | исключать шумные debug-логи, задавать retention |

Для оценки месячного счета нужны, как минимум: средние и пиковые запросы/с, размер каталога и частота обновления, доля cache hit, средний размер ответа, число заказов, доступность по SLA, выбранный регион и срок хранения данных. После нагрузочного теста сравнить стоимость на 1 000 поисков и на подтверждённое бронирование.

## 8. Надёжность и безопасность

- Search API и интеграционные адаптеры масштабируются независимо; отказ одного экземпляра не прерывает обслуживание.
- Elastic Cloud размещает реплики в разных зонах; потеря узла не должна делать индекс недоступным.
- Cloud SQL HA используется для production-заказов; PITR и восстановление проверяются регулярно.
- Поисковый индекс считается производной копией данных, его можно пересоздать из источников и событий.
- Все изменяющие операции бронирования идемпотентны; повтор события не создаёт двойной заказ или списание.
- Для внешних поставщиков заданы тайм-ауты, circuit breaker и ограниченные повторы с задержкой.
- Секреты API поставщиков хранятся в Secret Manager; сервисным аккаунтам выдаются минимальные роли.
- Пользовательские данные и платежные сведения не попадают в поисковые логи; доступ к логам ограничен.
- Включены Cloud Billing budgets и уведомления, лимиты Cloud Run, квоты партнёров и алерты по росту DLQ.

## Вывод

Для Travelio Booking предложена облачная архитектура GCP с Cloud Run, Elastic Cloud, Redis, Cloud SQL и Pub/Sub. Она масштабирует поиск, интеграции и бронирование независимо, поддерживает сезонное увеличение нагрузки и снижает влияние отказов отдельных компонентов.

Цель p95 < 1 секунды достигается сочетанием предварительной индексации, кэширования популярных запросов, параллельного поиска и ограничения ожидания внешних поставщиков. Согласованность цены и наличия проверяется перед оформлением заказа. Численные размеры ресурсов и бюджет необходимо подтвердить нагрузочным тестом и расчётом тарифов после уточнения фактической нагрузки.
